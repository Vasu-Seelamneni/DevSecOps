① OSI & TCP/IP Models

OSI Model (7 layers)
  • L7 — HTTP · Application layer
  • L6 — encryption · Presentation layer
  • L5 — Session · Session layer
  • L4 — TCP/UDP · Transport layer
  • L3 — Router (packets) · Network layer
  • L2 — Switches (frames) · Data link layer
  • L1 — Cables · Physical layer
TCP-IP Model: L7, L6, L5 → combined into one Application layer. L4, L3, L2, L1 stay separate.
DNS Resolution — Stage 1 ➜ TCP Handshake — Stage 2 ➜ Data Transfer

② IP Addressing

  • IP Address — unique identifier for a device on a network
  • CIDR — Classless Inter-Domain Routing (e.g. 10.0.0.0/16)
  • Subnet — logical subdivision of an IP network

🔒 Private IP

  • Always starts with 192 / 172 / 10.0.0.0
  • Used inside VPC/VNet

🌍 Public IP

  • Reachable from the internet
  • Used for external access

③ Ports 💡

Ports = communication endpoints on a device for each resource/service. e.g. 22 → SSH, 80 → HTTP, 443 → HTTPS, 3306 → MySQL.

④ Cloud Hierarchy — Azure vs AWS

  • Resource Groups — nothing but a logical name or boundary for grouping a set of resources
  • There are NO Resource Groups in AWS — instead it uses Regions to locate resources

Azure Hierarchy

  1. Root Management Group
  2. → Sub Management Groups
  3. → Subscriptions (billing boundaries)
  4. → Resources (cost mgmt)

AWS / IAM

  • Uses IAM account instead of RG's → Regions
  • Root account should NOT be used
  • MFA recommended
  • Account alias → e.g. citi / vedin / any_org
Azure identity = Entra ID (users u1,u2,u3… · groups G1,G2,G3… · policies)

⑤ IAM & Entra ID

AWS — IAM

  • Users (u1, u2, u3…)
  • Groups (G1, G2, G3…)
  • Policies (e.g. Storage Team)
  • Account Alias → citi / vedin / org

Azure — Entra ID

  • Users (u1, u2, u3…)
  • Groups (G1, G2, G3…)
  • Policies
  • Tenants — can join e.g. Citibank ↔ Citibank Loans

AWS services: EC2S3ECREKS

⑥ DNS Resolution — Stage 1 🌐

Why: The user types a domain (e.g. citi.com) → DNS resolves it to an IP address.
User types URL ➜ DNS lookup ➜ Get IP ➜ Then TCP Handshake (Stage 2)
